# Engineering conventions

## Supported setup and ownership

- Target fresh installations on Arch-based distributions. Preserve existing Arch-family detection, pacman/AUR integration and CachyOS/Garuda behavior; add no speculative hardware or OS compatibility.
- Both profiles receive the common workstation configuration: packages, non-secret dotfiles, Fish as the login shell, common system/user services, fonts, themes, icons, cursors and desktop preferences. Credentials, private applications, personal-only services, hardware configuration, Btrfs/Snapper, swap/hibernation, boot/security, enrollment and firewall provisioning remain personal-only. Never access personal credentials in nonpersonal mode. Keep profile conditions explicit; add questionnaires or feature flags only for actual requirements.
- Chezmoi owns managed files, templates, profile conditions, execution order and `run_before`, `run_after`, `run_once` and `run_onchange` semantics. Keep procedural workflows directly in Python run scripts under `home/.chezmoiscripts/linux/`; this directory accepts scripts only. A run script must contain its workflow rather than forward to a separate implementation module.
- Shared Python helpers belong in `home/.chezmoitemplates/lib/`. Extract only for multiple real consumers or to centralize an important correctness/security invariant. Imports must work from Chezmoi's rendered temporary scripts independently of the working directory; retain the explicit `/usr/bin/python3 -B` interpreter. Avoid custom loaders, installed provisioning packages and global `PYTHONPATH` configuration.
- Mise owns supported declarative packages, services and tasks. Preserve that ownership rather than duplicating it in Python. Fish owns interactive shell configuration.
- Python 3.14 is the primary provisioning language. Keep the initial missing-prerequisite installer in shell because Python may not exist yet; preserve its single missing-only package transaction. Use Bash where genuinely necessary, without forwarding wrappers that only invoke Python. Migrate retained provisioning Bash only within the authorized phase; shell-specific runtime configuration is outside that migration unless explicitly included.

## Design principles

Optimize for readability, correctness, maintainability and safe reapplication. Use the simplest implementation that expresses the required behavior without navigating multiple abstraction layers. Implement current requirements; prefer an explicit limitation over speculative compatibility or anticipated reuse.

1. **Keep the main path visible.** Reading `main()` should reveal a clear sequence of meaningful operations. Prefer guard clauses to deep nesting. Extract details for clarity or genuine reuse, not arbitrary function-length limits. Keep orchestration out of generic managers, registries and pipelines.
2. **Name domain behavior.** Use names such as `validate_root_mount()`, `configure_snapper()` and `needs_initramfs_rebuild()` rather than `process()` or `run_task()`. Avoid redundant module context in names; prefer precise names to explanatory comments.
3. **Make external boundaries explicit.** Pacman, Mise, Btrfs, Snapper, systemd, network access, privileged commands and filesystem writes have side effects. Validate important prerequisites before consequential operations. Use `subprocess.run()` directly with argument lists for straightforward commands; use `shell=True` only when shell semantics are genuinely needed. Separate complicated output parsing from unrelated workflow decisions. Shared subprocess helpers need real reuse or a significant safety guarantee, not a universal runner, adapter or class hierarchy.
4. **Represent meaningful states clearly.** Validate assumptions before changing state; reject unsupported filesystem, boot and authentication states with actionable errors. Failed inspection must not masquerade as missing configuration. Prefer precise return types, `Path`, enums or dataclasses when they clarify multiple outcomes; built-in types suffice for simple configuration without Pydantic or elaborate schemas.
5. **Separate decisions from actions where useful.** Inspect state, determine whether a change is needed, validate it, apply it and verify consequential results. Separate pure transformations from privileged effects when that improves readability, testing or rollback safety; keep trivial operations direct.
6. **Make failures useful.** Identify the operation and preserve real exit statuses and safe underlying diagnostics; never invent explanations from exit codes or suppress failures to report success. Use the shared Loguru configuration for concise terminal errors and useful private tracebacks. Avoid duplicate reports. Let unexpected exceptions propagate unless handling adds context, restores state or implements legitimate recovery.
7. **Keep each change coherent.** Preserve unrelated configuration. Delete superseded code, unused imports, helpers, wrappers and obsolete tests once replacements work. Keep functional corrections distinguishable from formatting changes where practical; favor independently understandable commits.

This unpublished architectural rewrite requires no compatibility with discarded dotfiles internals. Remove old execution paths, aliases, duplicate implementations, script-name shims and migration frameworks. Preserve existing data, supported fresh-install behavior, security boundaries and operational safeguards; these are distinct from obsolete compatibility.

## Python conventions and operational safety

- Follow Python 3.14, `ruff.toml` and `pyproject.toml`. Prefer ordinary control flow, cohesive functions, clear interface annotations, `pathlib`, context managers and the standard library. Add dependencies or classes only for concrete benefits. Avoid mutable global provisioning state, import-time side effects and clever expressions that obscure intent.
- Comments explain non-obvious constraints, invariants and decisions rather than repeat code. Broad `except Exception` handling requires a deliberate program boundary, necessary cleanup or safe reporting of an otherwise unhandled failure.
- Every workflow must tolerate intentional reapplication. Inspect actual state, skip correct configuration, preserve unmanaged entries, ownership and permissions, and avoid duplicate mounts, service activation, configuration entries and package operations. Avoid unnecessary restarts and rewrites.
- Validate privileged writes, preserve meaningful conflict detection and verify consequential results before success. Use atomic publication where partial writes would be harmful; create temporary files safely, clean them up and reject untrusted symlinks in privileged writes. Preserve protections for Btrfs, swapfiles, hibernation, Zswap, Limine, Secure Boot and credentials.
- Preserve safe retries after interrupted operations. Prefer actual state over custom completion markers; retain operational markers when they protect meaningful deferred or multi-step work. Add recovery only for real failure paths, without a generic rollback framework.
- Prefer sequential execution. Retain necessary locks for real shared-state risks; close files, descriptors and subprocess resources deterministically. Capture only needed output, bound streaming/resource use and use timeouts where appropriate. Preserve usable terminal input/output for interactive authentication and package-manager operations, along with meaningful failure statuses.

## Logging

Use the existing shared `configure_logging()` in `home/.chezmoitemplates/lib/provision_logging.py` for Python provisioning. Keep terminal output concise and TTY-aware, respect `NO_COLOR`, and preserve this format:

`[YYYY-MM-DD HH:mm:ss] [LEVEL] Message`

Persistent records additionally identify the native source filename and line. Preserve private XDG storage, directory permissions `0700`, file permissions `0600`, rotation/retention, unsafe-target protection and safe exception diagnostics with `diagnose=False` and `backtrace=False`.

Log meaningful changes, warnings and failures; keep successful no-ops quiet. Never log credentials, tokens, vault responses, sensitive arguments or environments. Preserve secret-safe diagnostics/redaction and do not report provisioning success after logging failure. Keep trivial operations direct rather than wrapping them to add logs. Do not introduce Rich, progress bars, spinners or another logging framework.

## Tests and validation

- Use native pytest functions, ordinary assertions, `tmp_path`, `monkeypatch` and small reusable fixtures under `.github/tests/`. pytest is the sole Python runner; migrate retained unittest-style tests incrementally alongside relevant changes rather than expanding that style.
- Test behavior with meaningful consequences: profile isolation, secret protection, fresh installs, idempotency, failure propagation, retry/interruption safety, filesystem/boot integrity and observed regressions. Prefer a few valuable integration tests and lightweight syntax/configuration checks over excessive mocks, fixture hierarchies, implementation snapshots or repeated invariants. Delete obsolete tests with obsolete code; avoid test-count/coverage quotas, trivial/cosmetic tests and hypothetical hardware matrices. Add no new testing framework.
- Contributors manage development tools themselves. Require Python 3.14, Ruff, BasedPyright and pytest on PATH; report missing or unsupported tools by executable name and fail without installing, bootstrapping or substituting them.
- Run `python3 -B .github/tests/validate.py` before committing Python changes. It coordinates Ruff lint/format checks, BasedPyright in recommended mode, pytest once, Chezmoi template validation, Bash/ShellCheck for retained shell and Mise configuration checks. Independent commands are documented in `.github/README.md`. Fix real violations rather than blanket exclusions or widespread suppressions; never claim an unavailable check passed.
- Validate both profiles of Python run templates and settings modifiers. Keep rendered paths unique and Python out of Bash checks. Explicitly discover relevant Python in hidden Chezmoi/test directories; verify with `basedpyright --verbose` and reject zero-file checks. Use `useDefaultExcludes = false` only when supported by the installed checker; retain exclusions for caches, virtual environments and generated files.
- Test privileged behavior in controlled environments. Do not modify the development host's live filesystem, boot configuration, services or desktop preferences merely for validation.

## Git and phase completion

- Continue in `refactor/dotfiles-simplification` and its existing worktree. Use `wt` with its installed supported syntax when branch/worktree management is necessary; avoid unnecessary branches or worktrees. Keep `main` untouched until the final reviewed PR.
- Use focused Conventional Commits. Sign every commit with the existing Git configuration and immediately verify with `git verify-commit`. Stop on signing failure; never bypass signing or weaken its configuration.
- Open one final PR only after all phases and integration validation, using `.github/pull_request_template.md`. Do not open intermediate PRs.
- End every implementation phase with a review in the final response: **What changed** (meaningful changes and removals), **Why it changed** (rationale and maintenance benefits), **What I should know** (behavior, safety, tradeoffs, limitations and maintenance implications), **Validation** (meaningful tests actually run and results), **Git status** (commits, signature verification, worktree and main/PR state), and **Next phase** (the next focused responsibility). Routine Git inspection is not a test. Do not create review documents by default or start another phase without explicit authorization.
- Write naturally in the repository owner's voice, developer to developer. Never refer to the owner as “the user” or narrate conversation requests/confirmations. Preserve applicable nested `AGENTS.md` guidance.
